# ผมสร้าง FIREKEEPER จากศูนย์อย่างไร

## เมื่อความผิดพลาดกลายเป็นเครื่องมือพัฒนา

ถ้ามีคนถามว่าผมสร้าง FIREKEEPER ขึ้นมาได้อย่างไร คำตอบอาจไม่ได้เริ่มจากเรื่อง AI การเขียนโปรแกรม หรือ Architecture แต่มันเริ่มจากวิธีที่ผมใช้เรียนรู้มาตลอด

สมมติว่าผมต้องทำข้อสอบ 100 ข้อ ผมจะไม่พยายามอ่านทุกอย่างจนมั่นใจว่ารู้ครบก่อนแล้วจึงเริ่มทำข้อสอบ แต่จะใช้ความรู้ที่มีอยู่ในขณะนั้นลองทำทันที ทำเสร็จแล้วตรวจคำตอบ ถ้าถูก 60 ข้อ ผิด 40 ข้อ ผมจะสนใจ 40 ข้อที่ผิด หาว่าทำไมถึงผิด ทำความเข้าใจ แล้วลองอีกครั้ง

ถ้ารอบต่อไปเหลือผิด 15 ข้อ พื้นที่ที่ต้องสนใจก็เหลือเพียง 15 ข้อ จาก 15 เหลือ 5 จาก 5 เหลือ 2 และสุดท้าย 2 เหลือ 0

ผมเพิ่งมาสังเกตภายหลังว่า วิธีเดียวกันนี้ถูกนำมาใช้กับการสร้าง FIREKEEPER แทบทั้งหมด

## ผมไม่ได้เริ่ม FIREKEEPER ด้วยคำตอบที่สมบูรณ์

FIREKEEPER ไม่ได้เกิดจากการที่ผมมี Architecture ที่สมบูรณ์อยู่ในหัวตั้งแต่วันแรก ผมไม่ได้รู้ล่วงหน้าว่าสุดท้ายระบบจะต้องมี Evidence Evaluation, Hypothesis Formation, Risk & Critique Analysis, Human Approval Gate หรือ Decision Audit ในรูปแบบใด

สิ่งที่มีในช่วงแรกคือแนวคิดหลัก:

> **AI assists. Humans decide.**

AI ไม่ควรเป็นผู้ตัดสินใจแทนมนุษย์ แต่ควรช่วยให้มนุษย์มองเห็นข้อมูล เหตุผล ความไม่แน่นอน และความเสี่ยงก่อนตัดสินใจ

จากแนวคิดนั้น ผมเริ่มสร้าง แล้วดูว่ามันผิดตรงไหน

## Build → Test → Find the Error → Fix → Repeat

วิธีพัฒนา FIREKEEPER ในทางปฏิบัติจึงตรงไปตรงมา:

**สร้าง → ทดสอบ → ตรวจ → หาเรื่องที่ผิด → แก้ → ทดสอบใหม่**

แล้วทำซ้ำ

บางครั้งผมเพิ่มระบบใหม่เข้าไปเพราะคิดว่ามันจำเป็น เมื่อใช้งานจริงจึงพบว่ามันซ้ำกับของเดิม ผมตัดออก

บางครั้ง Architecture ดูถูกต้อง แต่เมื่อดู Flow จริงกลับพบว่า LLM ได้รับ Prompt มากเกินความจำเป็น ผมลดมัน

บางครั้ง Code ทำงานแล้ว แต่ Documentation อธิบายไม่ตรงกับ Code ผมแก้ Documentation

บางครั้ง Documentation ถูก แต่ Test ยังทดสอบพฤติกรรมเก่า ผมแก้ Test

บางครั้ง Test ผ่านทั้งหมด แต่เมื่อทดลองใช้งานจริงกลับพบพฤติกรรมที่ไม่ควรเกิด วงจรก็เริ่มใหม่อีกครั้ง

## สิ่งที่ผ่านแล้ว ไม่ใช่พื้นที่หลักที่ต้องใช้เวลา

ถ้าระบบมี 100 จุด และตรวจแล้ว 80 จุดทำงานถูกต้อง ผมไม่ควรใช้เวลาเท่ากันกับทั้ง 100 จุดอีก ผมต้องรู้ว่า 20 จุดที่เหลือคืออะไร จากนั้นจัดการ 20 จุดนั้น

เมื่อตรวจใหม่อาจเหลือ 7 ก็ทำ 7 เหลือ 2 ก็ทำ 2

มันเหมือนการทำข้อสอบซ้ำโดยเน้นข้อที่ตอบผิด

**ความผิดพลาดจึงเป็นข้อมูลที่บอกว่า iteration ต่อไปควรไปทางไหน**

## นี่คือเหตุผลที่ FIREKEEPER เคยใหญ่กว่าที่ควรจะเป็น

ช่วงหนึ่ง FIREKEEPER สามารถทำหลายอย่างมาก มีหลาย LLM providers, Retrieval, Memory, Hosted Mode, Offline Mode, BYOK, Workspace, Publication, Admin, Mobile, Audit และระบบย่อยอีกจำนวนมาก

ถ้ามองจากจำนวน Feature นั่นอาจดูเหมือนความก้าวหน้า แต่คำถามที่สำคัญกว่าคือ:

> สิ่งเหล่านี้ทำให้ FIREKEEPER ทำหน้าที่หลักได้ดีขึ้นจริงหรือไม่?

เมื่อคำตอบของบางส่วนคือ “ไม่” สิ่งที่ต้องทำจึงไม่ใช่เพิ่ม Feature ต่อไป แต่คือ **ตัด**

ผมไม่ได้ถามแล้วว่า “เรายังสร้างอะไรเพิ่มได้อีก?” แต่เริ่มถามว่า “อะไรยังผิด? อะไรซ้ำ? อะไรไม่จำเป็น? อะไรทำให้แกนหลักอ่อนลง? อะไรที่ Test ผ่านแต่พฤติกรรมจริงยังไม่ถูก?”

## จากระบบที่ทำได้หลายอย่าง สู่ระบบที่รู้ว่าตัวเองควรทำอะไร

เมื่อสิ่งที่ไม่จำเป็นถูกลดลง แกนของ FIREKEEPER เริ่มชัดขึ้น ระบบไม่ได้มีหน้าที่เป็น AI ที่รู้ทุกอย่าง และไม่ได้มีหน้าที่ตัดสินใจแทนมนุษย์

แกนสำคัญอยู่ที่การทำความเข้าใจเจตนาและบริบท จัดโครงสร้างข้อมูล ประเมินหลักฐาน สร้างและท้าทายสมมติฐาน วิเคราะห์ความเสี่ยง สนับสนุนการตัดสินใจ และรักษาขอบเขตอำนาจของมนุษย์พร้อม Audit ที่ตรวจย้อนหลังได้

AI ช่วยวิเคราะห์ ช่วยเสนอสมมติฐาน ช่วยหาหลักฐานสนับสนุนและหลักฐานที่ขัดแย้ง ช่วยเปิดเผยความไม่แน่นอน และช่วยเตือนความเสี่ยง แต่เมื่อเป็นการตัดสินใจที่มีผลกระทบ ผู้มีอำนาจสุดท้ายยังต้องเป็นมนุษย์

## “ตรวจ” สำคัญกว่า “สร้าง”

ระหว่างพัฒนา FIREKEEPER มีคำหนึ่งที่ผมใช้บ่อยมาก:

**“ตรวจ”**

เมื่อ Feature ถูกสร้างเสร็จ ผมไม่ต้องการเพียงคำตอบว่า “เสร็จแล้ว” ผมต้องการรู้ว่ามันทำงานจริงหรือไม่ Test ผ่านหรือไม่ Flow ถูกหรือไม่ Prompt ที่ส่งให้ LLM จริง ๆ คืออะไร Evidence เข้าไปถึงขั้นตอนไหน Documentation ตรงกับ Implementation หรือไม่ และการแก้ครั้งนี้ทำให้ส่วนที่เคยผ่านแล้วพังหรือไม่

ดังนั้นคำว่า “ตรวจ” สำหรับผมจึงเหมือนการขอทำข้อสอบรอบใหม่

ถ้าตรวจแล้วพบว่ามีบางอย่างผิด นั่นไม่ได้แปลว่าการพัฒนาล้มเหลว ตรงกันข้าม เราเพิ่งค้นพบว่า iteration ต่อไปต้องทำอะไร

## Error-Driven Development มีจุดอันตราย

วิธีนี้ไม่ได้ถูกต้องโดยอัตโนมัติ เพราะ **ตัวตรวจต้องเชื่อถือได้**

ถ้าเฉลยผิด นักเรียนสามารถฝึกจนจำคำตอบผิดได้อย่างสมบูรณ์ Software ก็เช่นเดียวกัน ถ้า Test ผิด เราสามารถแก้ Code จนผ่าน Test ที่ผิดได้ ถ้าเกณฑ์ Audit ผิด เราสามารถ Optimize ระบบจนได้คะแนนสูงขึ้น แต่ผลิตภัณฑ์จริงกลับแย่ลง

ถ้า Evidence ที่ใช้ประเมินไม่น่าเชื่อถือ Hypothesis ที่ดูมีเหตุผลก็อาจตั้งอยู่บนฐานที่ผิด

นี่ทำให้ FIREKEEPER ให้ความสำคัญกับ Evidence provenance, Claim–Evidence relationship, Audit log, uncertainty, Human Approval และการตรวจสอบย้อนหลัง เพราะระบบที่สามารถ “ตอบ” ได้ ไม่ได้หมายความว่าระบบนั้น “เชื่อถือ” ได้

## จาก Prompt ยาว ๆ เหลือเพียงคำว่า “ต่อ”

เมื่อทำงานร่วมกันต่อเนื่อง Context เริ่มสะสม คำสั่งจึงสั้นลงเรื่อย ๆ จนบางครั้งเหลือเพียง “ต่อ” “ตรวจ” “แก้” หรือ “รวม”

ถ้าเอาคำว่า “ต่อ” ไปพูดกับคนที่ไม่เคยทำงานร่วมกัน เขาย่อมถามกลับว่า “ต่ออะไร?” เพราะคำสั่งแทบไม่มีข้อมูล

แต่เมื่อมี Shared Context เดียวกัน คำว่า “ต่อ” สามารถหมายถึง ตรวจสถานะล่าสุด อย่าย้อนทำสิ่งที่ผ่านแล้ว หาปัญหาถัดไป จัดการมัน ทดสอบ ระวัง Regression แล้วเดินต่อ

สิ่งนี้ทำให้เห็นความแตกต่างระหว่าง **Prompt** กับ **Working Context**

Prompt อาจสั้นมาก แต่ถ้า Context แข็งแรง การทำงานยังสามารถต่อเนื่องได้

## ผมไม่ได้ใช้ AI เพราะต้องการให้ AI คิดแทน

ผมไม่ได้ต้องการ AI ที่บอกว่า “นี่คือคำตอบที่ถูกต้อง เชื่อผม”

ผมต้องการ AI ที่สามารถบอกว่า นี่คือสิ่งที่เรารู้ นี่คือหลักฐาน นี่คือสิ่งที่เรายังไม่รู้ นี่คือสมมติฐาน นี่คือสิ่งที่ขัดแย้งกับสมมติฐานนั้น นี่คือความเสี่ยง และนี่คือจุดที่มนุษย์ต้องตัดสินใจ

เพราะนี่เป็นวิธีเดียวกับที่ผมใช้เรียนรู้

ผมไม่ต้องการซ่อนข้อที่ทำผิด ผมต้องการรู้ว่า **ข้อไหนผิด**

## ความผิดพลาดคือแผนที่

เส้นทางของ FIREKEEPER จึงไม่ได้เป็น:

**Idea → Perfect Architecture → Development → Finished Product**

แต่มันใกล้กับ:

**Idea → Build → Test → Fail → Inspect → Fix → Test Again → Remove → Simplify → Audit → Repeat**

หลายครั้งสิ่งที่ทำให้ระบบดีขึ้นไม่ได้มาจากการเพิ่มอะไรเข้าไป แต่มาจากการค้นพบว่าอะไรผิด แล้วเอามันออก หรือพบว่าสิ่งที่คิดว่าถูกนั้นยังไม่มีหลักฐานเพียงพอที่จะเรียกว่าถูก

ถ้าต้องสรุปวิธีสร้าง FIREKEEPER จากศูนย์เป็นประโยคเดียว:

> **ผมเริ่มจากสิ่งที่รู้ในตอนนั้น ลงมือทำ เปิดให้มันถูกทดสอบ แล้วใช้สิ่งที่ผิดเป็นแผนที่สำหรับรอบต่อไป**

ไม่จำเป็นต้องทำถูก 100 ข้อตั้งแต่รอบแรก แต่ต้องรู้ให้ได้ว่า **ข้อไหนผิด และทำไมถึงผิด**

บางที FIREKEEPER เองก็เกิดจากหลักการเดียวกัน ไม่ใช่ระบบที่พยายามทำให้ AI “ถูกเสมอ” แต่เป็นระบบที่พยายามทำให้มนุษย์ **มองเห็นว่าตรงไหนอาจผิด ก่อนที่จะตัดสินใจ**

**มองให้ลึก ก่อนตัดสินใจ**
